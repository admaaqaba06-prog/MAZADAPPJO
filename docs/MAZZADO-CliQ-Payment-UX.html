1. What this document is

Every screen shown here is rendered from the shipped code, not from a mockup. The Arabic and English copy is quoted verbatim from the source. Where something is not built, this document says so rather than implying otherwise — see §6.

The one thing to read first. Our backend does not yet call the CliQ API. The flow below creates a request record, drives the full state machine and renders every screen, but no request reaches a bank. That is why the rail is disabled in production. We would rather show you the finished interface and an honest gap than a demo that implies a connection we have not made.

EN: “Make sure to pay from your CliQ account at: Bank al Etihad” · “Payments are usually processed in real time. However, in some cases, processing may take up to 2 hours.” · “Acknowledge the note above to enable the button.”

Bank lookup. Characters 5–8 of the IBAN are matched against the official code list you supplied. An unrecognised code falls back to neutral wording (“the bank linked to your account”) and never blocks payment — we do not guess a bank name on a payment screen. One correction for your records: the onboarding note said the last four characters of the 8-character code are sufficient to match. The data says the first four — UBSIJOAX against JO21UBSI…; the trailing JOAX/JOAM are BIC country and location halves and never appear in an IBAN. Matching on the last four would resolve every Jordanian bank to one of two values.

4. The 90-minute duplicate rule

You test this, so it is worth being precise about where it is enforced. Not in the browser. The check runs inside a database transaction on a trusted backend, so a refresh, a second tab, or a replayed call cannot mint a second request. A buyer who is blocked sees a live countdown rather than a dead button:

لديك طلب دفع قيد الانتظار. لا يمكنك إنشاء طلب جديد لنفس الدفعة حتى تتم الموافقة عليه أو تنتهي صلاحيته — الوقت المتبقي 73:00.

Expiry is derived from the timestamp, not waited for. If a notification never arrives, the payer is not locked out forever — the window simply lapses and they may retry. A request that is pending with no expiry recorded fails closed and holds the lock.

Question for Staq. Is the 90-minute window authoritative on your side, or advisory? If we submitted a second request for the same payment anyway, is it rejected, does it supersede the first, or could both be approved by the payer? We have assumed rejection and would like that confirmed rather than inferred.

5. Receiving alias

We understand the requirement that the gateway alias must not be the business name, so that gateway payments (which fire notifications) stay distinguishable from manual transfers sent straight to the public alias.

Our public alias is MAZZADO26, at Bank al Etihad, and it is the live destination for manual transfers today. We will register a separate technical alias for the gateway and hold it in secret storage, never in source control. Because both rails now sit at Bank al Etihad, the two are otherwise indistinguishable on one statement — which we read as making the separate alias more necessary, not less.

Question for Staq. Please confirm the naming constraints, and whether you recommend a separate account behind the gateway alias for reconciliation.

6. What is not built yet

Stated plainly so the review is not based on an assumption:

  • No API call. The payment-request endpoint is not called. The integration points are marked in code and the request id is minted locally so the interface and state machine can be exercised end to end.
  • No webhook verification. We have reserved a secret for it and will not go live without it. We now have the X-Finto-Signature format from your documentation and will verify against it.
  • No production certificate in use. The signed certificate has not been committed to source control and is excluded by policy.
  • Gateway alias not yet registered (see §5).
  • Automatic verification is deliberately off. A bank-confirmed payment still passes our human verification step before funds are released to a seller. This is our own conservatism; if you consider gateway confirmation sufficient to skip it, tell us.

7. Remaining questions

  1. Reconciliation key. We send ExternalTransactionId and expect it back as TransactionId. One example in your documentation shows "TransactionId": null. If it can genuinely arrive null, we cannot map a payment back to an order except by alias and amount, which is ambiguous. Can we rely on it being present?
  2. Out-of-order notifications. Can an expired arrive after a paid? We currently treat paid as terminal and ignore anything after it.
  3. Cancelling a pending request. Can a merchant revoke a request before the payer acts? Our marketplace gives a winner a payment deadline; if that lapses while a request is outstanding, the lot may already have moved to the runner-up. We have made that case safe — the payment is recorded and escalated, never silently dropped — but we would rather prevent it.
  4. Rejection notifications. Your documentation describes a payment notification only. Is there any callback for a request the payer declines, or does it simply expire?
